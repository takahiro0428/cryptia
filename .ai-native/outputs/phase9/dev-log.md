## 設計判断

- **プロキシの安全設計:** 任意 URL の中継はしない（エンドポイント固定・addrs は base58 検証・1〜30 件制限）。
  IP 単位 30/分のレートリミット + 短期インメモリキャッシュ（8〜90s）+ 同一キーの inflight 合流で
  上流レートリミット（DexScreener 約 300/分）を保護。上流失敗は 502 `CRYPTIA-E102` に正規化
- **直接取得優先:** プロキシ常用は Cloud Functions の呼び出しコストとレイテンシを増やすため、
  直接取得 → 失敗時のみプロキシの sticky 切替とした。プロキシも失敗したら次回は直接から再試行（自己回復）
- **発見パイプラインの共通化（原則3):** `discoverFreshPairs()` は fetchJson 注入型として shared に置き、
  サーバールートとクライアント直接フォールバックの双方で同一ロジックを使用。スコアリングも shared で共通
- **未取得シグナルの扱い:** RPC・再発行照合の失敗は `null`（不明）とし、加点も減点もしない。
  null による「回避」誤判定はしない（クライアント直接フォールバック時は SNS・流動性のみで評価）
- **スナイプの既定ラダー:** メミコインの現実（急騰後の全戻しが多い）に合わせ、+50% で元本の一部を
  早期回収する利益確保型。ムーンバッグ 20% を残して大きな伸びも取れる設計

## デプロイ後の追加障害対応（イテレーション 3）

デプロイ後の本番で「CRYPTIA-E102: DexScreener の応答に Solana ペアがありません」を確認
（= 接続断ではなく、**search?q=SOL の応答から Solana ペアが得られない**事象。Phase 9 の
エラーコード表示強化により原因の特定が可能になった）。対策:

- **スクリーニングの多ソース化**（`discoverScreeningPairs`）: search に加え token-boosts
  （宣伝中トークン）・token-profiles（掲載直後トークン）→ tokens 解決の 3 ソースを
  Promise.allSettled で収集し pairAddress で重複排除。単一 API の応答変化・地域差で空にならない
- **経路判定を内容ベースに変更**: 直接取得が HTTP 200 でも「使えるトークン 0 件」なら失敗として
  プロキシへ切替（企業ネットワークの改変応答・フィルタ応答は transport 成功のまま内容が空になるため）
- **サーバー側も全ソース空を 502 扱い**にし、空リストをキャッシュしない（stale があれば劣化継続）
- `fetchPairsForTokens` を共通化し fresh パイプラインと共用（原則3）

## 追加機能: 自動スナイプ（常時監視）モード（イテレーション 4）

オペレーター要望「新規トークンを監視して最低限の監査にかけて随時トレードを進めるモード」への対応。

- **第 4 の取引手法 `auto-snipe`:** トークンの事前選択が不要。ティック（30s）ごとに新規上場リスト
  （発行 48h 以内）を監視し、監査通過トークンへ空き枠の範囲で随時エントリー。
  出口はスナイプと同じ利益確保型ラダー（SNIPE_LADDER_RULES）を共用
- **最低限の監査（`shared/snipeScoring.ts` `passesMinimalAudit`）:** 総合判定（候補のみ / 設定で要注意まで）+
  流動性 $5k 以上 + mint/freeze 権限の残存が**判明していない**こと + 同名再発行 2 件未満。
  null（未取得）は拒否しない — 「取得できない」と「危険と判明」を区別し、照合 API の一時障害で
  全エントリーが止まらないようにする
- **資金管理:** 1 枠 = 割当資金 ÷ 最大同時ポジション数（1〜10・既定 5）。エントリー済みペアへの
  再エントリーは行わない（`enteredPairs` 永続化。ラグ後の再急騰への誘い込み対策）
- **安全ガード:** モックデータ中・監視データが 5 分超過に古い場合はエントリー見送り
  （実勢と乖離した価格での執行防止）。セッション世代ガード（ISSUE-3 と同水準）適用
- UI: 手法タブに「自動スナイプ」追加（Radar アイコン）、設定（最大同時数・監査基準）、
  監視ステータス（新規上場 N 件 / 監査通過 M 件 / 累計エントリー K 件）をフォーム・ダッシュボード両方に表示
- **レビュー指摘の反映:** 全量決済済みペアの監視剪定（30 件バッチ枠の温存 + 保有ポジション優先の
  価格取得 = 長期稼働でも出口ルールが止まらない）、執行直前の最新価格再取得、
  設定値の正規化一本化（`normalizeAutoSnipe`）、enteredPairs の上限間引き（詳細: review-results.md イテレーション 4）
- テスト: `passesMinimalAudit` 単体 7 件 + 自動スナイプ結合 7 件（監査ゲート・枠管理・再エントリー防止・
  モック/鮮度ガード・世代ガード・剪定・直前価格）→ **145 件全パス**

## 追加機能: ムーンバッグモード（イテレーション 11）

オペレーター要望「出始めのトークンを最速で買って、100% 上昇で 70% を売却して放置して利益を出しつつ、
魔界トークンを保持する自動取引」への対応。既存とは別の取引手法 `moonbag` として追加した。

- **エントリー:** 自動スナイプと同一パイプライン（常時監視・最低限の監査・等分予算・ミント単位の
  再エントリー防止・執行直前の価格再取得）。`usesAutoPipeline()` で 2 手法を統一的に扱う
- **出口:** `buildMoonbagLadder()` — +100% 到達で 70% 売却（元本の 1.4 倍 = 元本+40% を確定回収）→
  残り 30% は**売却ルールなしのムーンバッグとして恒久保持**（`positionMeta.moonbagAt` を記録し、
  損切り含む全ルールを triggered 充填で無効化）
- **推奨設計 1 — 損切り選択制:** 損切りなし（完全放置）の損益分岐は「約 71% が +100% に到達」という
  非現実的な前提のため、既定 -50%（-30/-70/なしを選択可・+100% 到達前のみ有効）。null は明示選択のみ、
  省略時は推奨値（サイレントに損切りなしへ落ちない）
- **推奨設計 2 — 枠の温存:** ムーンバッグ化した保有は**同時ポジション数に数えない**
  （恒久保持が新規エントリー枠を塞いで監視型戦略が機能停止する問題の予防）
- **推奨設計 3 — 価格枠の保護:** 価格取得 30 件枠は「アクティブ保有（執行に直結）→ ムーンバッグ
  （表示専用・ローテーションで順繰り更新）→ その他監視ペア」の優先順に割り当て。ムーンバッグが
  増えても執行用の価格鮮度を劣化させない
- **整合性:** moonbag セッションのラダールールは復元時に設定（`moonbagStopLossPct`）から再構築
  （設定が SoT。改変データでも表示と実行が乖離しない）。追加フィールドは加算的（原則7）
- **UI:** 手法タブ「ムーンバッグ」・損切りセレクト（なし選択時は損益分岐の警告表示）・
  セッションカードのムーンバッグ保有サマリー（件数・評価額）・ポジション行の「ムーンバッグ保持中」
  バッジ・ポジション詳細の保持状態表示（ラダー残ラインの代替）
- テスト: 結合 11 件（TP/放置/枠除外/損切り/損切りなし/復元正規化 + レビュー反映で
  履歴間引き保護・価格バケット優先・ローテーション・評価額の 4 件追加）+ 単体 5 件 → **176 件全パス**

## 追加機能: ボットウォレット自動実行（イテレーション 12）

オペレーター要望「自分しか使わないため、署名は一度行ってその後は署名せずに自動取引を行いたい」への対応。
拡張ウォレットは取引ごとの承認が必須（自動承認 API なし）のため、**専用トレード用ウォレット
（ボットウォレット）方式**で実現した（BR-1 改訂・F-13）。

- **鍵管理（`shared/botKeyStore.ts`）:** アプリ内で専用生成した鍵ペアを PBKDF2-SHA256（310k 反復）+
  AES-GCM でパスフレーズ暗号化し、**端末 localStorage にのみ**保存（Firestore 同期なし）。
  平文鍵は実行中のモジュール変数のみ（リロードで消滅 → 再開はパスフレーズ再入力）。
  作成直後に base58 の秘密鍵バックアップを一度だけ表示
- **自動執行（`stores/botTrade.ts`）:** デモと同じ監視・監査ゲート（フレッシュプール・
  passesMinimalAudit・5 分鮮度・モック中停止）で、Jupiter スワップをボット鍵で署名し
  RPC 経由で送信。出口はデモと同じラダー（自動スナイプ = 利益確保型 / ムーンバッグ = +100% で
  70% 売却 → 残り保持）。売却は raw 数量の BigInt 配分（浮動小数誤差なし）
- **安全装置:** 専用ウォレット限定（メインの鍵は扱わない）・SOL 建て上限（1 回のエントリー額 ×
  最大同時数・1 日の投入上限）を署名前に強制・リスク同意必須・緊急停止・価格影響 10% 超は不執行・
  出金は作成時登録のメインウォレット宛のみ・手数料予約 0.01 SOL
- **RPC プロキシ拡張:** 許可メソッドへ `sendTransaction`（署名済み Tx の中継のみ・base64 検証・
  サイズ上限）/`getLatestBlockhash`/`getSignatureStatuses` を追加（メソッド別バリデータ化。
  プロキシは署名能力を持たない）。入金はウォレット署名 1 回の SOL 送金（`wallet.sendSol`）
- **設計判断:** ボットの状態（設定・ポジション・ログ）も端末ローカル限定（鍵と同じ端末に閉じる）。
  実行はアプリを開いている間のみ（サーバー常駐化はカストディ責任が質的に変わるため見送り）
- テスト: 鍵暗号化 5 + BigInt 配分 1 + エンジン結合 16（エントリー/上限/残高/価格影響/停止条件/
  ムーンバッグ出口/損切り/開始・出金ガード/復元 + 監査反映: 確定確認・実残高照合・改竄復元・
  AAD 改竄・日次ロールオーバー・出金）+ RPC バリデータ単体 5 → **204 件全パス**（詳細: review-results.md イテレーション 12）
- Playwright: ボット UI 9 項目（セットアップ警告・パスフレーズ・未接続ガード）+ live 回帰 PASS
